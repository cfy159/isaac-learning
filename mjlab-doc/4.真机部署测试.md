# 真机部署测试（Lite3-Walk-Flat）

> 前置：第 3 篇的训练与 ONNX 导出。本篇把 `logs/rsl_rl/lite3_velocity_walk/2026-10-14_16-06-38/` 里的 `policy.onnx` 部署到真机，用 [xgo_doglib](https://github.com/LuwuDynamics)（`XGO_DOG` 串口库）搭一条**实验级**闭环链路，并把「怎么确定策略输入/输出每个参数的含义」讲成一套可复用的方法。测试脚本：`xgo-robot/lite3_deploy_test.py`。

## 0. 训练产物盘点

| 文件 | 内容 | 部署用得上吗 |
|---|---|---|
| `policy.onnx` | 策略网络（只含 actor，`obs[1,53] → actions[1,14]`） | ✅ 核心，onnxruntime 推理 |

## 1. 怎么确定输入/输出参数含义（方法论）

策略是一个 `53 维进 → 14 维出`的黑盒网络。**含义不是猜的，是有权威出处的**，按下面四步拿证据。

### 1.1 第一步：读 ONNX 元数据（权威来源）

luwu 的 `VelocityOnPolicyRunner` 在导出时把关键信息写进了 ONNX 元数据（`mjlab/rl/exporter_utils.py` 的 `attach_metadata_to_onnx`）。一条命令读出来（任何装了 onnx 的 Python 环境）：

```python
import onnx
m = onnx.load("policy.onnx")
for p in m.metadata_props:
    print(p.key, "=", p.value)
print(m.graph.input[0].name, [d.dim_value for d in m.graph.input[0].type.tensor_type.shape.dim])
```

你的 `lite3_velocity_walk` 检查点的实际输出（我已读取核实）：

```
joint_names = FL_hip_joint,FL_thigh_joint,FL_shank_joint,FR_hip_joint,...,RL_shank_joint,mainarm_joint,forearm_joint
default_joint_pos = 0.000,0.950,0.000, 0.000,0.950,0.000, 0.000,0.950,0.000, 0.000,0.950,0.000, -1.550,1.300
observation_names = base_ang_vel,projected_gravity,command,phase,joint_pos,joint_vel,actions
action_scale = 0.25
输入: obs [1, 53]   输出: actions [1, 14]
```

| 元数据字段 | 含义 |
|---|---|
| `observation_names` | **观测项的拼接顺序**（这是 53 维布局的目录） |
| `joint_names` | 14 个动作分量对应的关节（**注意顺序是 FL,FR,RR,RL**，不是 FL,FR,RL,RR！） |
| `default_joint_pos` | 默认位型（rad）：大腿 0.95、双臂 -1.55/1.3，其余 0 |
| `action_scale` | 动作缩放 |

### 1.2 第二步：维度验算，拼出 53 维布局

各观测项的维度来自 `params/env.yaml`（或直接看第 2 篇的观测表）：

| # | 观测项 | 维度 | 单位/含义 | 验证方法 |
|---|---|---|---|---|
| 0-2 | base_ang_vel | 3 | 机身角速度，rad/s，机体系 | 陀螺仪 |
| 3-5 | projected_gravity | 3 | 重力单位向量在机体系的投影，静止时 ≈ [0,0,-1] | IMU 欧拉角/加速度计 |
| 6-8 | command | 3 | [vx, vy, wz] 速度指令，机体系 | 遥控/键盘给定 |
| 9-10 | phase | 2 | 步态时钟 sin/cos，周期 0.4s | 程序内部时钟 |
| 11-24 | joint_pos | 14 | 关节角相对默认位型，rad | 舵机角度传感器 |
| 25-38 | joint_vel | 14 | 关节角速度，rad/s | 舵机角度差分 |
| 39-52 | actions | 14 | 上一拍策略输出（原样，未乘 scale） | 程序内部状态 |

验算：3+3+3+2+14+14+14 = **53** ✓（对不上就说明某项理解错了，这个算术是最好的自检）。

### 1.3 第三步：输出 14 维的含义

`actions ∈ [-1,1]` 附近，含义是**相对默认位型的关节角度偏移**（第 2 篇动作模块）：

```
目标角度(rad) = default_joint_pos[i] + 0.25 × action[i]
```

14 个分量按 `joint_names` 顺序对应关节。策略同时控制双臂关节——它学会的是把臂保持在默认位置附近（pose 奖励），部署时照常下发即可。

### 1.4 第四步：三个必须精确复刻的公式

这些在仿真里是函数，真机上要逐字重写（源码位置都验证过）：

**① command 排布**（`src/tasks/velocity/mdp/velocity_command.py`）：`[vx, vy, wz]`，机体系，指令模长 < 0.1 视为站立。

**② phase 时钟**（`src/tasks/velocity/mdp/observations.py`）：

```python
ph = (t % 0.4) / 0.4 * 2π;  phase = [sin(ph), cos(ph)]   # 指令≈0 时置 [0,0]
```

**③ projected_gravity**（mjlab 内置 `projected_gravity`，由 roll(φ)/pitch(θ) 重构）：

```python
proj_g = [sin(θ), -sin(φ)·cos(θ), -cos(φ)·cos(θ)]   # 静止时 ≈ [0, 0, -1]
```

交叉验证：静止时加速度计读数 `acc ≈ -9.81 × proj_g`——标定时用它核对 IMU 轴向。

## 2. 真机接口盘点：xgo_doglib 能给什么

`XGO_DOG`（`xgolib/xgolib_dog.py`）走串口协议（115200），和策略需求对账：

| 策略需要 | 库提供 | 差距/解法 |
|---|---|---|
| 机身角速度 | `read_imu()[3:6]`（deg/s） | ×π/180 转 rad/s；**轴向待标定** |
| 重力投影 | `read_imu()[6:8]`（roll/pitch） | 代入 §1.4③ 公式重构 |
| 关节角 | `read_motor()`（15 个舵机，**度**） | 转弧度、减默认位型 M0；**ID 映射待标定** |
| 关节角速度 | ❌ **库不提供** | 相邻两拍角度差分（÷dt） |
| 下发关节目标 | `motor([ID 列表], [角度列表])`（度） | 目标 = M0 + SIGN×deg(0.25×action) |
| 速度指令 | — | 键盘/参数给定（`--vx/--vy/--vyaw`） |

两个固有的坑，提前知道：

1. **控制频率**：策略按 50Hz 训练（0.004s×5），而串口每拍要发 14 个单舵机帧 + 2 次读，115200 波特率下能不能顶到 50Hz 要实测（脚本每 100 拍打印实际频率）。**低于 30Hz 策略大概率站不稳**——好在训练加了 1~2 拍延迟模拟（第 3 篇），对慢环有一定容忍度。
2. **伺服行程**：`motor()` 会自动把目标角裁剪到舵机行程内（xgolite 参数表），不会发疯，但映射错了依然可能摔倒——所以有下面的标定流程。

## 3. 标定：确定 P / SIGN / M0 / G_SIGN

真机和仿真之间有四个未知数，**全部可以用只读操作标出来**：

| 未知数 | 问题 | 标定方法 |
|---|---|---|
| `P`（ID 映射） | 仿真关节 `FL_hip`…对应哪个舵机 ID（11..43）？ | 卸力（`unload_allmotor`）后**逐腿单动**：一次只扳一个关节，看 `read_motor()` 里哪个 ID 在变；四个角的位置（左前/右前/右后/左后）肉眼分辨 |
| `SIGN`（方向） | 仿真正方向 = 舵机角度增大方向吗？ | 在仿真 `play.py` 里把该关节滑块 +0.1 rad，记下腿怎么动；真机同样动一下（或看 `read_motor` 读数增减），同向 +1 反向 -1 |
| `M0`（零点） | 默认站姿下舵机读数是多少度？ | `reset()` 让狗站到固件默认姿（≈仿真默认位型），此时 `read_motor()` 的读数就是 M0 |
| `G_SIGN`（IMU 轴向） | 陀螺仪三轴正方向和仿真一致吗？ | 抬鼻子/左倾/左转各做一次，看 `read_imu` 的 gyro 和 roll/pitch 变号方向，对照仿真预期 |

提示：双臂大概率是舵机 **52/53**——`xgolite` 参数里这两个舵机的行程（[-115,70]°、[-85,100]°）正好容得下 mainarm(-88.8°)/forearm(74.5°) 的默认角，是个强线索，但仍以实测为准。

`--stage calib` 就是干这个的：卸力、循环打印 15 个舵机角度 + IMU，你摆姿势抄数，填回脚本顶部的 `P / SIGN / M0 / G_SIGN` 四个常量。

## 4. 测试脚本：lite3_deploy_test.py

分五个阶段，**顺序不能乱**（每个阶段都是下一阶段的保险）：

```bash
# 板载电脑上（xgolib 已 pip install）
python3 lite3_deploy_test.py --stage calib     # ① 只读：标定四常量并填入脚本
python3 lite3_deploy_test.py --stage obs       # ② 只读+推理：静止时 proj_g≈[0,0,-1]、pos_rel≈0
python3 lite3_deploy_test.py --stage hold      # ③ 发 M0 保持站姿：验证 P/M0 执行链路
python3 lite3_deploy_test.py --stage policy    # ④ 策略闭环，零指令站立（架空！）
python3 lite3_deploy_test.py --stage policy --vx 0.2   # ⑤ 小指令前进
```

脚本核心就三段，对照 §1 的分析看：

```python
# 观测：53 维按元数据顺序拼
pos_rel = SIGN * np.radians(read_deg - M0)              # joint_pos（相对默认位型）
vel_rel = (pos_rel - prev_pos) / dt                     # joint_vel（差分）
obs = concat([gyro, proj_g, cmd, phase, pos_rel, vel_rel, prev_action])

# 推理
action = session.run(["actions"], {"obs": obs[None]})[0][0]

# 动作 → 舵机目标角（度），限幅 10°/拍 保平安
target_deg = M0 + SIGN * np.degrees(0.25 * action)
```

内置保护：M0 未填不让进 hold/policy；每拍动作限幅 `SAFETY_MAX_DELTA_DEG`；Ctrl+C 触发 `stop() + reset()` 急停回正；每 100 拍打印实际控制频率。

## 5. 安全清单与已知局限

**安全**：④⑤ 阶段**必须架空**（吊起或垫高，四脚离地）；地面测试先拴绳；每次上电先 `read_battery()`；第一次 policy 只给零指令。

**局限（诚实说）**：

- 这是**实验级链路**。串口库一拍 14 帧指令 + 2 次读，实测频率可能到不了 50Hz；频率不足时策略表现打折。产品级部署跑在板载底层接口上（固件级控制环），不走这条串口命令通道——本篇的价值是把「策略 ↔ 机器人」的每个参数含义打通。
- `read_imu` 的欧拉角换算用的是 3.14 而不是 π（约 0.05% 误差），可忽略。
- 若实测动作幅度明显比仿真里大/小，说明某关节存在传动比差异，在目标角公式里补一个逐关节 SCALE 即可。
- joint_vel 用差分近似（真实传感器没有），配合训练时的延迟模拟，实测通常可用；若抖动明显，可对差分加一阶低通。

## 6. 小结

- 确定参数含义的证据链：**ONNX 元数据（顺序/默认位型/scale）→ env.yaml（各项参数）→ 维度验算（53=11+42）→ 仿真源码公式逐条复刻**。
- 真机侧四件标定：`P`（ID 映射）、`SIGN`（方向）、`M0`（零点）、`G_SIGN`（IMU 轴向），全部只读可测。
- 部署五阶段：calib → obs → hold → policy(零指令) → policy(小指令)，每步都有明确的通过标准。
